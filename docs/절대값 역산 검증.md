# 절대값 역산 및 검증

네이버 데이터랩 API의 ratio(0~100)에서 실제 절대값(검색 횟수, 클릭 횟수)을 역산하는 방법과 검증 과정

관련 스크립트:
- `pipeline/collection/ratio_to_absolute.py` — 역산 알고리즘 (공유 모듈)
- `pipeline/collection/estimate_shopping_click_absolute.py` — 쇼핑 클릭 역산
- `pipeline/collection/estimate_search_absolute.py` — 검색 트렌드 역산
- `pipeline/collection/verify_shopping_click_absolute.py` — 쇼핑 클릭 검증 (round-trip)
- `pipeline/collection/verify_search_absolute.py` — 검색 트렌드 검증 (round-trip + 교차 + 앵커)

---

## 문제 정의

### API가 반환하는 값

네이버 데이터랩 오픈API는 검색량·클릭량을 **절대값이 아닌 상대 비율**로 반환

```
ratio[t] = value[t] / max_value × 100    (소수점 5자리 truncation)
```

`max_value`는 조회 기간 내 해당 키워드의 최대 일별 값. 최대일의 ratio가 100이 되고 나머지는 비례 축소. 키워드마다 독립 정규화되므로 **"포카칩"의 ratio 50과 "오란다"의 ratio 50은 전혀 다른 절대값**

### 절대값이 필요한 이유

virality_score의 정의:

```
virality_score = future14_max / past60_mean
```

상대값(0~100)으로 계산하면 이미 역대 최고 근방에 있는 키워드는 성장 여력이 있어도 높게 표시됨. 절대값이 있어야 실질적인 성장 배율을 측정 가능

## 핵심 아이디어: ratio에서 정수 격자 포착

### 관찰

키워드의 ratio 시계열을 유니크 값으로 정렬하면 **일정한 간격**이 반복됨

```
포카칩의 유니크 ratio (오름차순 일부):
  17.67822, 17.72639, 17.77456, 18.20809, 18.35260, ...

인접 diff:
  0.04817,  0.04817,  0.43353,  0.14451, ...
```

0.04817이 반복적으로 등장. 이 규칙적 간격의 정체는 **절대값이 정수**라는 사실에서 비롯

### 일정한 간격이 생기는 이유

API의 정규화 공식을 역으로 풀면:

```
value[t] = ratio[t] × max_value / 100
```

절대값(value)은 항상 정수(검색 1회, 클릭 1회 단위). 정수 1 단위의 변화는 ratio 공간에서 다음과 같이 나타남:

```
Δratio = 1 / max_value × 100 = 100 / max_value
```

따라서 **ratio 값들 사이의 최소 간격(min_diff)은 정수 1칸에 해당**하고, 이로부터 max_value를 역산 가능:

```
min_diff ≈ 100 / max_value
max_value ≈ 100 / min_diff
```

> "ratio 소수점 아래의 규칙적 패턴은 정수 격자의 그림자" — 이 관찰이 전체 방법론의 출발점

## 역산 알고리즘

### max_value 추정

```python
unique = sort(unique(ratios[ratios > 0]))    # 양수 유니크 값 정렬
diffs = diff(unique)                          # 인접 diff
diffs = diffs[diffs > 1e-6]                   # 부동소수점 노이즈 제거
min_diff = min(diffs)                         # 최소 간격 = 정수 1칸
base = round(100 / min_diff)                  # 1차 추정
```

### 후보 탐색

min_diff가 항상 정확히 1칸에 대응하지는 않음. 데이터에 연속 정수가 없으면 min_diff가 2칸, 3칸일 수 있고, truncation 오차로 실제보다 살짝 클 수도 있음. 이를 보정하기 위해 base의 **배수와 약수를 함께 탐색**:

```python
candidates = set()
for m in [1, 2, 3, 4, 5]:
    candidates.add(base × m)          # 배수: min_diff가 2칸이었다면 base×2가 정답
    candidates.add(base // m)         # 약수: truncation으로 base가 과대 추정된 경우
```

배수가 필요한 경우 — 데이터에 연속 정수가 없어서 min_diff가 실제 1칸보다 큰 경우. 예를 들어 min_diff가 2칸에 해당하면 base는 정답의 절반이 되므로, base×2에서 정답을 발견

약수가 필요한 경우 — truncation 오차로 min_diff가 실제보다 살짝 작게 관측되어 base가 과대 추정된 경우. base//2, base//3 등에서 정답을 발견

### 정수 복원 검증

각 후보 mv에 대해 모든 ratio를 절대값으로 변환하고, **정수에 얼마나 가까운지** 검사:

```python
for mv in sorted(candidates):
    restored = ratios × mv / 100
    errors = |restored - round(restored)|
    if all(errors < 0.05):       # 모든 값이 정수 오차 0.05 미만
        return mv                # 이 mv가 정답
```

0.05 임계값의 의미: ratio의 소수점 5자리 truncation이 최대 0.00001의 오차를 유발하고, 이것이 mv를 곱하면 최대 `mv × 0.00001 / 100` 정도. mv=50,000이어도 0.005 수준이므로 0.05는 충분한 여유

모든 후보가 실패하면 base를 fallback으로 반환 (실험 결과 fallback도 정확했음)

### 절대값 복원

```python
absolute[t] = round(ratio[t] × max_value / 100)
```

결과는 키워드×일 매트릭스(wide format)로 `data/raw/{source}/absolute.csv`에 저장

### 수치 예시: 포카칩

```
데이터 로딩
    1,520일, 양수 1,520개, 유니크 387개

최소 diff
    유니크 ratio 정렬 → 인접 diff 계산
    min_diff = 0.04816

base 추정
    base = round(100 / 0.04816) = 2,076

후보 탐색
    {415, 519, 692, 1038, 2076, 4152, 6228, 8304, 10380}

검증
    mv=415: restored에서 정수 오차 > 0.05인 값 존재 → FAIL
    mv=519: FAIL
    ...
    mv=2076: 모든 값의 정수 오차 < 0.05 → PASS (max_error=0.000207)

복원 예시
    2022-01-01: ratio=23.55491 → 23.55491 × 2076 / 100 = 489.0 → 489
    2022-01-02: ratio=26.49325 → 26.49325 × 2076 / 100 = 550.0 → 550
    2022-01-03: ratio=24.18111 → 24.18111 × 2076 / 100 = 502.0 → 502
    2022-01-05: ratio=92.00385 → 92.00385 × 2076 / 100 = 1910.0 → 1,910

결론: 포카칩의 조회 기간 최대 일일 검색량 = 2,076회
```

## 검증 설계

2가지 검증을 수행 (round-trip + 교차 비교)

### 검증 1: round-trip (오프라인, API 호출 없음)

역산한 절대값에서 ratio를 재계산하고 원본 ratio와 비교

```
reconstructed_ratio[t] = absolute[t] / max_value × 100
error[t] = |reconstructed_ratio[t] - original_ratio[t]|
```

**오차 범위**: 절대값을 정수로 반올림할 때 최대 0.5의 오차가 발생하므로 `max_error ≤ 0.5 / max_value × 100 = 50 / max_value`

max_value가 100이면 최대 오차 0.50으로, ratio 공간에서 0.5 차이. max_value가 1,000이면 최대 오차 0.05, 10,000이면 0.005로 거의 완벽. max_value가 클수록 복원 정밀도가 높아지며, 이 패턴이 실측에서도 나타나는지가 검증 포인트

**한계**: 내부 일관성만 확인. 역산 추정 자체가 systematic하게 틀리면 round-trip은 통과하되 실제 절대값과 다를 수 있음 → 검증 2가 필요한 이유

### 검증 2: 교차 비교 (API 호출, 2라운드)

역산값과 완전히 독립적인 경로로 절대값을 검증

#### 검증에 사용하는 변수

**overall_max** — 5개 키워드를 일괄 조회했을 때 API가 정규화에 쓰는 기준값. 5개 키워드의 모든 날짜 중 가장 큰 절대값. 예를 들어 A의 피크가 2,076이고 B의 피크가 3,818이면 overall_max = 3,818. API는 이 값을 100으로 놓고 나머지를 비례 축소

**cross_ratio** — 일괄 조회에서 반환되는 ratio. 개별 조회 ratio와 다름. 개별 조회에서는 포카칩 피크일 ratio가 100(자기 기준)이지만, 일괄 조회에서는 오란다가 더 크므로 3,818 기준으로 2,076/3,818×100 = 54.4가 됨

**expected_cross** — 역산으로 추정한 absolute에서 "일괄 조회하면 이 값이 나와야 한다"고 계산한 기대값. `absolute[kw][t] / overall_max × 100`으로 산출하며, 실제 API 반환값(cross_ratio)과 비교하여 오차 측정

**anchor** — 배치 5개 중 데이터가 가장 풍부한 키워드 3개. 이 키워드들의 개별ratio÷cross_ratio 비율로 actual_overall_max를 역산하는 데 사용. 역산 추정값만으로 계산한 overall_max가 아니라, API가 실제로 사용한 overall_max를 독립적으로 구하는 장치

**anchor_ratio** — 앵커 기준으로 역산한 max_value ÷ 역산 추정 max_value. 1.0이면 역산값과 앵커가 일치, 0.5면 역산값이 절반으로 틀렸다는 뜻

#### API의 교차 정규화 동작

키워드를 개별 조회하면 자기 자신의 피크가 100. 5개를 한 번에 조회하면 5개 중 가장 높은 키워드의 피크가 100이 되고, 나머지는 그에 비례하여 축소

```
개별 조회: ratio[t] = value[t] / 자기 피크 × 100        (자기 기준)
일괄 조회: ratio[t] = value[t] / 5개 중 최대 피크 × 100  (공통 기준)
```

일괄 조회에서는 키워드 간 절대 크기 비교가 가능 — 이것이 교차 비교의 핵심 원리

#### round-trip이 못 잡는 오류

절대값이 전부 공통 인수를 공유하면(예: 전부 짝수) max_value가 실제의 절반으로 추정될 수 있음. 모든 값이 일관되게 축소되므로 round-trip은 정상 통과

교차 비교는 서로 다른 키워드 5개를 한 배치로 묶음. 한 키워드의 max_value만 틀려도, 일괄 조회의 공통 기준에서 기대값과 실제값이 어긋남 → 오류 검출

다만 1,520일 독립 시계열에서 모든 일별 값이 공통 인수를 가질 확률은 현실적으로 0에 수렴

#### 검증 로직

역산으로 추정한 absolute에서 일괄 조회 시 나올 것으로 **기대되는** cross ratio를 계산하고, 실제 API 반환값과 **날짜별 전체 비교**:

```
expected_overall_max = max(max_abs[A], max_abs[B], max_abs[C], max_abs[D], max_abs[E])

각 키워드, 각 날짜:
    expected_cross[kw][t] = absolute[kw][t] / expected_overall_max × 100
    actual_cross[kw][t]   = API 반환값
    error[t]              = |expected_cross[t] - actual_cross[t]|
```

역산 추정이 맞다면 error ≈ 0 (truncation 수준). 하나라도 틀리면 배치 전체의 cross ratio가 어긋남

#### 배치 스케줄링

```
라운드 1: 500개 키워드를 랜덤 셔플 → 5개씩 100배치 → 각 키워드 1회 검증
라운드 2: 다시 셔플 → 5개씩 100배치 → 각 키워드 2회 검증 (다른 조합)
```

- 키워드당 정확히 2회, 서로 다른 배치 구성원과 함께 검증
- 총 200 API 호출 (0.5초 sleep 기준 ~100초)

#### 쇼핑 클릭 API 제약

네이버 쇼핑인사이트 API는 복수 키워드 일괄 조회를 지원하지 않음 → 교차 비교 불가, round-trip만 수행

#### 앵커 이중 체크 (안전장치)

교차 비교의 보완. 검증 2에서 "expected가 맞다"고 가정하고 비교하는데, 만약 배치 내 모든 키워드의 역산값이 동일한 방향으로 틀렸다면 검증 2가 이를 놓칠 수 있음

앵커 체크는 **다른 경로로 overall_max를 역산**하여 이중 확인:

```
배치 내 데이터 커버리지 상위 3개 키워드를 앵커로 선정

앵커의 개별 ratio와 교차 ratio 비율로 actual_overall_max 역산:
    앵커 A의 특정 날짜 t에서:
        개별 ratio = 50.0   (max_A 기준)
        교차 ratio = 25.0   (overall_max 기준)
        → overall_max = max_A × 50.0 / 25.0 = max_A × 2

    전체 날짜에서 이 비율의 중앙값 = actual_overall_max

각 키워드의 절대값을 앵커 기준으로 재추정:
    anchor_estimated_max[kw] = max(cross_ratio[kw]) × actual_overall_max / 100

역산 추정값과 비교:
    anchor_ratio = anchor_estimated_max / max_abs
    → 1.0에 가까울수록 정확
```

### 오차 해석

round-trip max_err 0.021의 의미:

```

max_value=100 기준: 0.021회 (사실상 0)
max_value=2076 기준: 0.44회 (반올림 범위 내)
```

교차 비교 mean_err 0.001의 의미: 날짜별 전체 비교에서 ratio 기준 0.001 차이. API truncation 수준의 미미한 오차

## 스크립트 구조

### 역산

`estimate_shopping_click_absolute.py`는 `data/raw/shopping_click/trend.csv`를 읽어 `data/raw/shopping_click/absolute.csv`를 출력. `estimate_search_absolute.py`는 `data/raw/search/trend.csv`를 읽어 `data/raw/search/absolute.csv`를 출력

`ratio_to_absolute.py`에 공유 함수 3개를 정의하여 4개 스크립트가 import로 공유: `estimate_max_value()`, `convert_to_absolute()`, `roundtrip_check()`

### 검증

`verify_shopping_click_absolute.py`는 round-trip 검증을 수행하고 `outputs/metrics/verify_shopping_click.csv`를 출력. `verify_search_absolute.py`는 round-trip + 교차 + 앵커 검증을 수행하고 `outputs/metrics/verify_search.csv`와 `outputs/logs/verify_search_*.jsonl`을 출력

쇼핑 클릭은 API가 복수 키워드 일괄 조회를 미지원하여 round-trip만 수행

#### verify_shopping_click.csv 컬럼

`keyword`는 키워드명, `max_abs`는 역산 추정 절대 max, `rt_mean_err`는 round-trip 평균 오차, `rt_max_err`는 round-trip 최대 오차

#### verify_search.csv 컬럼

`keyword`는 키워드명, `max_abs`는 역산 추정 절대 max, `rt_mean_err`와 `rt_max_err`는 round-trip 평균/최대 오차. `v1_mean_err`와 `v1_max_err`는 라운드1 교차비교 평균/최대 오차, `v1_anchor`는 라운드1 앵커 역산 비율로 ~1.0이면 정상. `v2_*` 컬럼은 라운드2에 대해 동일 구조

JSONL 로그는 배치별 API 요청/응답 상세를 기록 (request body, HTTP 상태, 응답 키워드 수, 에러)

### 실행


## 한계

- **소수점 truncation**: API가 소수점 5자리에서 자르므로, max_value > 100,000인 초고볼륨 키워드에서 개별 ratio의 복원 오차가 커질 수 있음 (max_value 추정 자체는 정확)
- **비공식 역추론**: API의 정규화 공식(`ratio = value / max × 100`)은 공식 문서에 명시되지 않은 역추론. 향후 API 변경 시 무효화 가능
- **쇼핑 클릭 교차 비교 불가**: 쇼핑인사이트 API가 복수 키워드 일괄 조회를 지원하지 않아 round-trip만으로 검증. 다만 검색 트렌드와 동일한 정규화 방식을 사용하므로 역산 알고리즘의 유효성은 동일하게 적용
